# ADR 0017 — Browser connections and temporary permissions V2

Status: Accepted under the owner's implementation request, contingent on two independent local boundary reviews of the exact candidate commit and passing targeted local gates before normal merge. No publication, deployment or production activation is authorized.

Extends ADRs 0013, 0015 and 0016. Airodrom continues to own canonical Mission authority, signed contracts, CapabilityBroker invocations, current Runs, read leases, independent evidence verification and owner Acceptance. Public web tools remain available to qualified local host/OpenCode Missions through the existing broker; execution workers gain no direct browser or network authority. Ordinary conversation, Memory, Vault, Gmail, service lifecycle and fish/menu rendering retain their existing contracts.

The connection menu has seven choices: existing Chrome, owned loopback CDP, isolated persistent browser, human-guided regular Chrome, human login, bounded Extended public browsing and cancel. Availability is configuration discovery; actual browser qualification occurs on open. A missing engine or failed ownership check is unavailable. No arbitrary external endpoint or caller-selected profile is accepted.

Chrome 136+ default-profile debugging restrictions are respected. Chrome 144+ now provides a documented explicit enablement and per-connection permission flow, but Airodrom has no qualified adapter that safely confines it to the approved target and preserves unrelated tabs. Existing ordinary Chrome therefore remains unavailable. The menu explains the supported upstream mechanism without claiming Airodrom access.

Owned CDP starts Chrome only after operator consent in a separate fixed private profile namespace. The original persistent-context launch handle retains process termination authority and the scoped TLS proxy remains locked until guards are installed. The sole permitted endpoint comes from fresh, regular, owned, single-link DevToolsActivePort metadata, hardened to 0600. The websocket path and loopback address are constrained; listener UID, direct parent process and executable identity are verified with bounded metadata, never raw arguments. File identity/content and listener identity are rechecked after attachment. No ordinary Chrome profile, cookie, password, token or storage export is read. The CDP connection uses the owned context; closure disconnects it and closes the original owning handle. Unverified termination retains canonical quarantine and the profile lease; status reports uncertainty explicitly.

Session consent seals connection mode, exact site, purpose, Strict/Authentication mode and expiry into the immutable Mission contract. Strict permits fixed GET/HEAD feature routes and approved assets only. Authentication permits human-controlled same-site POST at fixed existing-login/MFA endpoints, with the previously observed Monarch static/root catalog when explicitly selected. Expiry and hand-back drain sockets and pending navigation before Strict inspection. Revocation aborts the canonical operation and closes the owned browser. Request admissions (100), encrypted transport bytes (16 MiB), redirect-chain (3), total redirects (20), actions and signed runtime budgets remain bounded; transport exhaustion latches and closes the browser. No budget exhaustion can reopen a fresh connection.

No external identity catalog is qualified. Google/Microsoft/Apple OAuth requests, identity popups, unknown methods/endpoints and query-bearing authentication URLs stay denied. Dedicated browser window.open and credential/passkey APIs remain disabled. Synthetic OAuth fixtures prove those limitations and sanitized ERR_BLOCKED_BY_CLIENT request/redirect diagnostics; they do not establish real Monarch OAuth support or access account data. The menu offers human-guided regular Chrome for those login flows. No MFA/CAPTCHA bypass or credential capture is provided.

The owner can grant Extended public discovery for a qualified Mission with explicit GET/HEAD purpose, domain/action/request/byte budgets and a deadline up to fifteen minutes, intersected with the immutable Mission deadline. Existing standalone research Missions remain capped at three minutes. Strict/on and Extended/all must match. Extended always uses a fresh unauthenticated context, never the persistent account profile. Search and PDF stay unavailable without a real qualified provider/reader.

Blocked diagnostics retain only a sealed/catalogued origin, fixed route class, method/resource class and reason. Unknown origins are redacted because hostnames can themselves contain personal data. Query/body/header/cookie values and private paths are absent. Only fixed feature-category evidence leaves account DOMs; authenticated screenshots, downloads, financial values, mutations, settings changes and payments remain denied. Reports compare verified evidence classifications with current approved Arecibo docs/code, and recommendations do not execute.

Compatibility: existing manual profile directory and data remain intact; CDP uses a distinct namespace. Existing grants keep their original ceilings. No new dependency, secret store, workflow trigger, migration of Chrome data or public release is introduced. New commands and operator Control Center controls are additive. Qualification and review evidence are recorded in the PR and accompanying local report. Hosted Actions remain disabled.

Primary references: [Chrome debugging restrictions](https://developer.chrome.com/blog/remote-debugging-port), [Chrome 144 explicit session connection](https://developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session), [Playwright browser connections](https://playwright.dev/docs/api/class-browsertype).
